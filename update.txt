BUG-12 — Consultation/Today's Collected showing ₹0
Root cause: get_doctor_today_summary() computed "today's collected" by finding appointments dated today and summing whatever their invoices had ever collected — completely missing payments made today for appointments from other days (e.g., a backlog of unpaid visits getting settled). I verified this against live data for a real doctor: the old query returned ₹300, the corrected one (keyed off Payment.payment_date == today instead of appointment date) returned ₹1,060 — ₹760 of real cash collected today was being silently dropped. Also changed the "Consultation ₹0" fee badge to show "Fee not set" instead of a misleading ₹0 when a doctor's rate was never configured (the DB defaults it to 0, not null).

The "Refer to Doctor" action was a dead-end: it called the referral API directly without saving the referring doctor's own clinical notes/medicines/optical Rx first, silently discarding anything typed. Fixed details

Issue #57 — Revenue shows full amount before payment
Root cause: the "Today's Revenue" figure on both the Pharmacy and Optical dashboards was summing the full billed amount of every sale (total_amount), not what was actually collected (paid_amount). A sale with an advance/partial payment was counted as full revenue immediately.
Fix: both dashboards (and their 30-day trend charts) now sum paid_amount instead of total_amount. Revenue now only reflects money actually collected, and updates correctly as more of the balance gets paid.

Issue #56 — Optical billing/payment tracking issues
Root cause: optical sales already stored payment status, advance amount, and balance — but there was no way to view that breakdown or collect a remaining balance after the sale was created.
Fix: added a "Receive Payment" action (adds to the amount already collected, so an existing advance is preserved) and a "View" action showing the full breakdown (items, subtotal, tax, advance, collected, balance, status) on the Optical Sales list. Also added Payment/Status columns to the list so it's clear at a glance.

Issue #55 — Product can be dispensed twice in optical
Root cause: nothing checked whether a prescription had already been sold against before creating a new sale — a second tab, a stale link, or revisiting the prescription page could dispense it again and double-deduct stock.
Fix: the system now rejects creating a second sale for a prescription that's already been dispensed, with a clear "already dispensed" message and badge on the prescription page. A database-level safeguard was also written (not yet applied — see below) to block this even under simultaneous requests.

Issue #51 — Stock adjustments fail to be created (pharmacy)
Root cause: the adjustment was actually being saved successfully, but the server crashed while building its response (an internal ID formatting bug), so the app displayed "Failed" even though the change had gone through — meaning retrying could apply it a second time.
Fix: corrected the response formatting. Adjustments now save and return successfully in one attempt, with no silent double-apply risk.

Issue #50 — Second batch with same batch number doesn't increase inventory
Root cause: the system treated any batch with the same batch number as identical, even if the manufacturing/expiry dates were different — so a second shipment reusing a batch number either silently merged into the wrong batch (losing its real expiry date) or got rejected outright as a duplicate.
Fix: batches are now identified by batch number and manufacturing/expiry date together, so two shipments with the same batch number but different dates are correctly tracked as separate batches and both add to stock.

Issue #48 — No validation on manufacturing/expiry dates
Root cause: there was no check anywhere preventing a future manufacturing date or a past expiry date.
Fix: added validation everywhere these dates are entered (GRN receiving, batch add/edit, opening stock for new medicines/products) — manufacturing date can no longer be in the future, and expiry date can no longer be in the past, both in the form itself and on the server.

Issue #46 — Refund doesn't restore inventory
Root cause: the restock logic did work, but if the original batch had since been marked inactive (e.g. after running out), the refund still added stock back to it — invisibly, since inactive batches are excluded from stock totals shown everywhere else.
Fix: when a refund restocks a batch that had been deactivated, it's now reactivated at the same time, so the returned quantity is immediately visible in stock again.

Issue #39 — Last name should require more than 2 letters

Issue #42 — "Waiting" count wrong after OPD assignment

Fixed to use the appointment's actual date, and added the same date check to the doctor-workload count used by the "Send to Doctor" screen.

Issue #41 — Doctor doesn't see notifications for new patients

Issue #40 — Consultation fee doesn't update

## Issue #43 — Username not autogenerating; no hospital-code enforcement

**Two separate creation paths exist, only one works correctly:**
- **Add Staff/User** (existing hospital): `user_service.suggest_username()` (`backend/app/services/user_service.py:141-183`) already correctly builds `HospitalCode + First2(first) + First2(last) + "_" + seq` and the frontend (`StaffModals.tsx:401-420`) live-fills it. **Not broken.**
- **Super Admin → Create Hospital** (the actual bug): `SuperAdminCreateHospital.tsx:310-317`'s own `suggestUsername()` builds `emailprefix_timestamp` — no hospital code at all, because **the hospital code doesn't exist yet at the point this form is filled out** (`tenant_service.py:134`, `code = generate_tenant_code()`, only generated after submission). The backend fallback (`tenant_service.py:193-195`) only appends the code when the field is left blank, and never validates a manually-typed username at all.

**Fix — enforce the hospital code server-side, since the client structurally cannot know it in advance:**

`backend/app/services/tenant_service.py`, right after `hospital` is flushed (has `.id`/`.code`, ~line 178), replace lines 193-195:
```python
requested_username = (admin_user_data.get('username') or '').strip().lower()
if not requested_username:
    # Reuse the same hospital-code-based template as ordinary staff creation
    # (user_service.suggest_username) for consistency across both flows.
    from .user_service import suggest_username
    requested_username = suggest_username(
        db, hospital.id, admin_user_data.get('first_name') or '', admin_user_data.get('last_name') or ''
    )
else:
    # The admin typed something before the hospital code existed — it can't
    # possibly already contain it, so guarantee inclusion server-side rather
    # than rejecting a value the user had no way to get right.
    code_prefix = code.lower()
    if not requested_username.startswith(code_prefix):
        requested_username = f"{code_prefix}_{requested_username}"
```
(existing uniqueness check right after is unchanged).

**Frontend** (`SuperAdminCreateHospital.tsx:310-317`): replace the email+timestamp suggestion with a name-based one (mirroring the staff-creation generator's spirit — first-few-letters of admin name rather than email), and update the helper text near the username field to note the hospital code is added automatically. Cosmetic/UX only — the backend now guarantees correctness regardless of what reaches it.

No Pydantic schema validator is added for "must contain hospital code" — it's provably impossible to check at that layer since the code doesn't exist until after the `Hospital` row is created, later in the same request.

## Issue #42 — "Waiting" count wrong after OPD assignment (future follow-ups counted as waiting today)

**Root cause:** `assign_doctor_to_walkin` (`backend/app/routers/walk_ins.py:717-792`) hardcodes `queue_date=today` (line 767) when creating the `AppointmentQueue` row, regardless of the appointment's actual `appointment_date` — so a future-dated follow-up run through this endpoint gets a queue row dated today. The main queue list (`GET /walk-ins/queue`) correctly double-filters `queue_date == target AND Appointment.appointment_date == target` (`walk_ins.py:328-335`) so it's unaffected — but `GET /walk-ins/queue/doctor-loads` (`walk_ins.py:881-912`, backing the "Send to Doctor" modal's "N waiting" badge, `WalkInQueue.tsx:1721,1748`) only filters on `queue_date`, so it counts the mismatched row.

**Fix:**
- `walk_ins.py:767` — `queue_date=appt.appointment_date` instead of `queue_date=today` (matching the already-correct pattern in `refer_patient_to_doctor`, which uses `queue_date=referral_date`).
- `walk_ins.py:895-905` (`get_doctor_queue_loads`) — add `Appointment.appointment_date == load_date` to the filter, mirroring `/walk-ins/queue`'s pattern, so a stray mismatched row can't be counted even if one already exists.

## Issue #40 — Consultation fee doesn't change when updated

Editing `Doctor.consultation_fee` **does** persist correctly today. The real bug: every appointment snapshots its own fee at booking time (`resolve_new_appointment_fee`, from the earlier consultation-fee fix), and once set, `resolve_consultation_fee_amount` (`invoice_service.py:597-624`) always preferred that frozen snapshot — so editing the doctor's rate never affected an appointment that was already booked, even if nothing has been billed yet. Per your confirmation: unbilled appointments should re-sync to the doctor's current rate; already-invoiced appointments must stay locked to what was actually charged.

**Fix:**
1. **`invoice_service.py::resolve_consultation_fee_amount`** — check whether the appointment already has an invoice; if not, prefer the doctor's *current* rate over the frozen `appointment.consultation_fee`; if it does, keep the frozen value authoritative (never rewrite an already-billed amount):
```python
def resolve_consultation_fee_amount(db: Session, appointment: Appointment, has_invoice: Optional[bool] = None) -> Decimal:
    if has_invoice is None:
        has_invoice = db.query(Invoice.id).filter(
            Invoice.appointment_id == appointment.id, Invoice.is_deleted == False,
        ).first() is not None

    doctor_fee = Decimal(appointment.doctor.consultation_fee) if appointment.doctor and appointment.doctor.consultation_fee is not None else None
    appt_fee = Decimal(appointment.consultation_fee) if appointment.consultation_fee is not None else None

    if not has_invoice and doctor_fee is not None and doctor_fee > 0:
        return doctor_fee
    if appt_fee is not None:
        return appt_fee
    if doctor_fee is not None and doctor_fee > 0:
        return doctor_fee
    # ... existing hospital-default cascade unchanged ...
```
2. **`appointment_service.py::enrich_appointment` / `enrich_appointments`** — both already look up the appointment's most recent invoice (lines ~514-528, ~552-585). After that lookup, overwrite `d["consultation_fee"]` with `resolve_consultation_fee_amount(db, appt, has_invoice=consultation_invoice is not None)` so every display surface that reads an appointment (Queue badge, appointment lists, doctor summary) shows the same live-until-billed value instead of the raw frozen column — one canonical precedence rule used everywhere, not just at invoice-creation time.

## Issues #52 / #53 / #54 — Batch number visibility in Stock Movements and Inventory Adjustments

Both `StockMovement` and `StockAdjustment` (`backend/app/models/inventory.py:147,171`) already have a `batch_id` column, and `StockAdjustmentCreate` already accepts `batch_id` end-to-end (schema, service, and the batch-delta application logic) — it's just never surfaced as a human-readable batch number, and the generic Inventory Adjustments screen has no way to select one when creating an adjustment (unlike the legacy `pharmacy/StockAdjustments.tsx` screen, which already has a working batch `<select>` to model from).

**Backend — resolve `batch_id` → `batch_number` (fixes #52 and #53's data gap):**
- `inventory_service.py` — new helper next to `_resolve_item_name` (line 37):
```python
def _resolve_batch_number(db: Session, item_type: str, batch_id: Optional[uuid.UUID]) -> Optional[str]:
    if not batch_id:
        return None
    if item_type == "medicine":
        row = db.query(MedicineBatch.batch_number).filter(MedicineBatch.id == batch_id).first()
    elif item_type == "optical_product":
        row = db.query(OpticalBatch.batch_number).filter(OpticalBatch.id == batch_id).first()
    else:
        return None
    return row[0] if row else None
```
- Wire into `_format_movement_response` (line 1119-1135) and `_format_adjustment_response` (line 1391-1406): add `"batch_number": _resolve_batch_number(db, m.item_type, m.batch_id)` (and same for `adj`).
- `schemas/inventory.py` — add `batch_number: Optional[str] = None` to `StockMovementResponse` (line 279-296) and `StockAdjustmentResponse` (line 328-344).

**Frontend:**
- `types/inventory.ts` — add `batch_number: string | null` to `StockMovement` and `StockAdjustment` interfaces.
- `StockMovementsPage.tsx` — its "Batch" column already exists but renders the raw UUID (`m.batch_id`, line 132); change to `m.batch_number || '—'` (#52).
- `AdjustmentsPage.tsx` — add a "Batch" column to the list table (currently absent entirely, `:196-211`), rendering `adj.batch_number || '—'` (#53).
- `AdjustmentsPage.tsx`'s "New Stock Adjustment" create modal (#54) — add a batch `<select>` after the Item field (~line 300-314), shown once an item is selected: fetch batches via `pharmacyService.getBatches(itemId)` or `opticalService.getBatches(itemId)` depending on `formData.item_type` (both already return `{batch_number, quantity, ...}[]`, same functions the legacy `pharmacy/StockAdjustments.tsx:112-121` selector already uses), list each as `{batch_number} (Qty: {quantity})`, and set `formData.batch_id` on selection — the create schema/type/service already accept and persist it (`StockAdjustmentCreate.batch_id`, already applied correctly by `create_stock_adjustment`), so this is purely a missing frontend control.
