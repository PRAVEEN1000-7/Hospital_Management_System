BUG-12 — Consultation/Today's Collected showing ₹0
Root cause: get_doctor_today_summary() computed "today's collected" by finding appointments dated today and summing whatever their invoices had ever collected — completely missing payments made today for appointments from other days (e.g., a backlog of unpaid visits getting settled). I verified this against live data for a real doctor: the old query returned ₹300, the corrected one (keyed off Payment.payment_date == today instead of appointment date) returned ₹1,060 — ₹760 of real cash collected today was being silently dropped. Also changed the "Consultation ₹0" fee badge to show "Fee not set" instead of a misleading ₹0 when a doctor's rate was never configured (the DB defaults it to 0, not null).

BUG-21 — Refer-to-doctor
The "Refer to Doctor" action was a dead-end: it called the referral API directly without saving the referring doctor's own clinical notes/medicines/optical Rx first, silently discarding anything typed. Fixed by making it a real "Save & Refer to Doctor" action — it now saves any drafted content first (skipping the "must have a medicine" requirement, since referring without prescribing is valid) and only proceeds to refer if that succeeds. Also pre-fills the Referral Reason field from the doctor's clinical notes instead of requiring a retype.

BUG-23 — Batch dispensing quantity mismatch
The quantity input let a pharmacist type up to the medicine's total stock across all batches, not the selected batch's own stock — so entering a quantity larger than the chosen batch could hold triggered a silent cross-batch split on the backend (which does auto-FEFO-split) with zero visibility to the pharmacist. Added a clear breakdown panel that shows exactly which batches (soonest-expiring first, confirmed the backend already sorts this way everywhere) will supply the shortfall, so nothing is silent anymore. Applied to both prescribed items and extra items.

BUG-25 — Invoice missing Returned/Change amount
Found the exact gap: the Totals section only rendered a "Balance Due" row when balance_amount > 0; when a patient overpays (balance goes negative), that row just disappeared with no substitute — confirmed against a real overpaid invoice in the DB (Total ₹200, Paid ₹210, Balance -10, silently showing nothing). Added a "Returned (Change)" row for the negative case.

BUG-26 — Consultation fee not collected in billing
The system already knew the fee was outstanding — it just showed a warning telling staff to go collect it separately at reception instead of collecting it itself. Since DispensingBilling.tsx already builds a real Invoice at payment time, I now prepend a "Consultation Fee" line item to that same invoice (using the combined invoice type that already supports mixing consultation + medicine items) and void the stray standalone consultation invoice that prescription-finalization auto-creates, so it's never double-billed. The Total, Cash Received, and Change now include it automatically.

BUG-27 — Net collected wrong after refund; no refund invoice
The "Net Collected" bug itself was already fixed earlier this session (PaymentList.tsx). Digging further, I found the same refund-blindness bug freshly baked into today's BUG-12 fix: get_doctor_today_summary summed raw Payment.amount for 'completed' payments, but a partially refunded payment stays 'completed' (only a full refund flips it to 'reversed') — so it overstated collections. Extracted a shared payment_net_amount() helper (amount minus reserved refunds) into payment_service.py and used it in both places, so this can't drift apart again. Also built the missing piece: a /refunds/{id}/pdf printable refund receipt (mirroring the existing invoice PDF), with a "Print Receipt" button wired into both InvoiceDetail.tsx and RefundList.tsx.

BUG-28 — Stock not restored after refund
Confirmed: process_refund only ever touched money (Invoice.paid_amount, Payment.status) — it never touched MedicineBatch.quantity or logged a StockMovement, because a Refund had no way to reference which line item or how many units were being returned. Added that link (nullable invoice_item_id + restock_quantity on Refund, migration written but not run per your standing rule), let staff pick "Medicine Being Returned" in the Request Refund modal, and on processing, restore the quantity to the exact batch it was dispensed from (traced via medicine + batch number) with a proper StockMovement audit entry.

BUG-30 — FIFO ordering
Found it in one line: get_pending_prescriptions sorted Prescription.created_at.desc() — newest first, the exact opposite of FIFO — which is why a patient waiting 20+ hours was buried under one waiting 5 minutes. Changed to ascending order on finalized_at (falling back to created_at), matching the same timestamp the on-screen "wait time" column already uses.

Fixed details

Issue #57 — Revenue shows full amount before payment
Root cause: the "Today's Revenue" figure on both the Pharmacy and Optical dashboards was summing the full billed amount of every sale (total_amount), not what was actually collected (paid_amount). A sale with an advance/partial payment was counted as full revenue immediately.
Fix: both dashboards (and their 30-day trend charts) now sum paid_amount instead of total_amount. Revenue now only reflects money actually collected, and updates correctly as more of the balance gets paid.

Issue #56 — Optical billing/payment tracking issues
Root cause: optical sales already stored payment status, advance amount, and balance — but there was no way to view that breakdown or collect a remaining balance after the sale was created.
Fix: added a "Receive Payment" action (adds to the amount already collected, so an existing advance is preserved) and a "View" action showing the full breakdown (items, subtotal, tax, advance, collected, balance, status) on the Optical Sales list. Also added Payment/Status columns to the list so it's clear at a glance.

Issue #55 — Product can be dispensed twice in optical
Root cause: nothing checked whether a prescription had already been sold against before creating a new sale — a second tab, a stale link, or revisiting the prescription page could dispense it again and double-deduct stock.
Fix: the system now rejects creating a second sale for a prescription that's already been dispensed, with a clear "already dispensed" message and badge on the prescription page. A database-level safeguard was also written (not yet applied — see below) to block this even under simultaneous requests.

Issue #51 — Stock adjustments fail to be created (pharmacy)
Root cause: the adjustment was actually being saved successfully, but the server crashed while building its response (an internal ID formatting bug), so the app displayed "Failed" even though the change had gone through — meaning retrying could apply it a second time.
Fix: corrected the response formatting. Adjustments now save and return successfully in one attempt, with no silent double-apply risk.

Issue #50 — Second batch with same batch number doesn't increase inventory
Root cause: the system treated any batch with the same batch number as identical, even if the manufacturing/expiry dates were different — so a second shipment reusing a batch number either silently merged into the wrong batch (losing its real expiry date) or got rejected outright as a duplicate.
Fix: batches are now identified by batch number and manufacturing/expiry date together, so two shipments with the same batch number but different dates are correctly tracked as separate batches and both add to stock.

Issue #48 — No validation on manufacturing/expiry dates
Root cause: there was no check anywhere preventing a future manufacturing date or a past expiry date.
Fix: added validation everywhere these dates are entered (GRN receiving, batch add/edit, opening stock for new medicines/products) — manufacturing date can no longer be in the future, and expiry date can no longer be in the past, both in the form itself and on the server.

Issue #46 — Refund doesn't restore inventory
Root cause: the restock logic did work, but if the original batch had since been marked inactive (e.g. after running out), the refund still added stock back to it — invisibly, since inactive batches are excluded from stock totals shown everywhere else.
Fix: when a refund restocks a batch that had been deactivated, it's now reactivated at the same time, so the returned quantity is immediately visible in stock again.
